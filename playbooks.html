THE PRACTICE DESK

Good process.
Clear next steps.

Twelve practical checklists for common incidents and defensive questions, each step tagged with its response phase. Use them to structure a discussion or a tabletop exercise.

CHOOSE A SCENARIO

Checks are kept only while this page stays open. Nothing is saved or sent. Checked steps reflect your review, not verification of a real system.

Identity & access

Suspicious sign-in

An unexpected successful sign-in deserves context before a conclusion.

Practice scenario

A hypothetical user signs in from an unfamiliar network and registers a new device.

Evidence to preserve

  • The alert and its event identifiers
  • Sign-in, session, and device registration logs
  • The list of active sessions and tokens before revoking them
  • Any MFA or recovery changes made since the sign-in

Common mistakes

  • Treating an unfamiliar address as proof of compromise
  • Confirming with the user through contact details in the event
  • Revoking sessions before recording them
  • Closing the case without checking other accounts

Exposure & prioritization

New exploited vulnerability

Turn an advisory into an asset-specific remediation decision.

Practice scenario

A new KEV entry appears to match a component in a public-facing application.

Evidence to preserve

  • The advisory version you acted on
  • Evidence of the running version before and after the change
  • Reachability findings for each affected asset
  • The decision record, including accepted risk

Common mistakes

  • Prioritizing from the severity score alone
  • Trusting a scanner match without checking the running asset
  • Applying a mitigation and never verifying it
  • Losing track of assets that could not be patched

0 of 5 review steps checked

Visibility & detection

A log source goes quiet

A collection gap is a question about visibility, not a threat verdict.

Practice scenario

An identity log source stops arriving while endpoint and network data continue.

Evidence to preserve

  • The last event received and its timestamp
  • Collector, agent, and pipeline status at the time
  • Recent configuration and schema changes
  • The list of detections that depend on the source

Common mistakes

  • Reading zero alerts as zero activity
  • Restarting a collector before recording its state
  • Fixing ingestion without checking the detections that depend on it
  • Forgetting to backfill or note the gap for later investigations

0 of 5 review steps checked

Malware & extortion

Ransomware in progress

Stop the spread first. Decide about recovery with evidence, not pressure.

Practice scenario

Several file servers show renamed files and a ransom note. One workstation is still encrypting.

Evidence to preserve

  • The ransom note and sample encrypted files
  • A memory image from at least one affected host
  • Authentication, endpoint, and firewall logs for the preceding weeks
  • Backup job history and restore-point details

Common mistakes

  • Powering off or reimaging before evidence is captured
  • Restoring onto a network the attacker can still reach
  • Contacting the attacker without legal and leadership involvement
  • Assuming no data left because nothing has been published

0 of 7 review steps checked

Identity & access

Reported phishing email

One report usually means more recipients. Find them before the attacker uses what they collected.

Practice scenario

A user reports an email linking to a sign-in page. Two colleagues received the same message.

Evidence to preserve

  • The original message with full headers
  • URL and attachment hashes
  • Mail trace results showing all recipients
  • Sign-in logs for everyone who clicked

Common mistakes

  • Forwarding the live message to colleagues
  • Opening links on a production workstation
  • Blaming the person who clicked
  • Closing the case after the purge without checking sign-ins

0 of 7 review steps checked

Identity & access

Business email compromise

When money is moving, the bank call comes before the investigation.

Practice scenario

Finance receives a request, apparently from a known supplier, to change bank details before a large payment.

Evidence to preserve

  • The fraudulent messages with full headers
  • Mailbox audit logs and sign-in history
  • Inbox and forwarding rules exactly as found
  • Payment records and all communication with the bank

Common mistakes

  • Replying in the same thread to verify the request
  • Deleting rules before recording them
  • Delaying the bank call to finish the investigation
  • Assuming only one mailbox is involved

0 of 7 review steps checked

Malware & extortion

Malware on an endpoint

Decide what ran, what it touched, and what credentials it could reach.

Practice scenario

Endpoint protection flags a process started by an office document, followed by a connection to an unfamiliar host.

Evidence to preserve

  • A memory image of the host
  • The sample itself, with its hash and original path
  • The endpoint process and network timeline
  • Proxy and DNS logs for the device

Common mistakes

  • Running the sample on a production machine
  • Deleting the file before recording its hash and path
  • Uploading sensitive files to public analysis services without checking policy
  • Returning the host to service without resetting credentials

0 of 7 review steps checked

Cloud & data

Leaked cloud access key

Deactivate first, then read the audit log. Deleting the commit fixes nothing.

Practice scenario

A secret scanner reports a cloud access key committed to a public repository six hours ago.

Evidence to preserve

  • An audit log export covering the whole exposure window
  • The commit and repository history
  • A list of resources and identities created in the window
  • Billing and usage data

Common mistakes

  • Only deleting the commit
  • Rotating the key without reviewing how it was used
  • Checking a single region
  • Reusing the same key in other places

0 of 7 review steps checked

Cloud & data

Suspected data exfiltration

Establish what moved before estimating what it means.

Practice scenario

Network monitoring shows a large overnight upload from a database server to an unfamiliar storage service.

Evidence to preserve

  • Network flow, proxy, and firewall logs
  • Database and application audit logs
  • The state of the source host
  • Any staging archives that are found

Common mistakes

  • Estimating impact from transfer volume alone
  • Stating that no data was taken before the analysis is done
  • Wiping the source system
  • Leaving the notification assessment for later

0 of 7 review steps checked

Applications & suppliers

Exploited web application

Attempts are constant. The question is whether one of them worked.

Practice scenario

Firewall and application logs show an injection request followed by an unfamiliar file appearing on the server.

Evidence to preserve

  • Web server, application, and firewall logs
  • A copy of any web shell or dropped file
  • A file-system timeline of the server
  • Database audit logs

Common mistakes

  • Patching and moving on without checking for persistence
  • Deleting a web shell before copying it
  • Trusting secrets that were stored on the server
  • Treating blocked requests as the full picture

0 of 7 review steps checked

Applications & suppliers

Third-party breach

Their incident becomes yours through whatever access and data they hold.

Practice scenario

A software supplier announces that its systems were compromised and customer data may be affected.

Evidence to preserve

  • Supplier notifications and correspondence
  • Logs of supplier account and integration activity
  • The inventory of shared credentials and when each was rotated

Common mistakes

  • Waiting for the supplier’s final report before acting
  • Assuming you are unaffected because you were not named
  • Rotating some shared secrets but not all
  • Forgetting dormant integrations

0 of 7 review steps checked

AI systems

Prompt injection against an assistant

Treat it as an access-control incident: what could the assistant do, and what did it do?

Practice scenario

An assistant with access to internal documents and a ticketing tool takes an unexpected action after summarizing an external web page.

Evidence to preserve

  • The full conversation and tool-call logs
  • The injected content and its source
  • Model and configuration versions
  • A record of every action the assistant took

Common mistakes

  • Relying on a system prompt as the only control
  • Giving an assistant broader permissions than its user
  • Dismissing it as the model simply making a mistake
  • Deleting the session before saving it

0 of 7 review steps checked
