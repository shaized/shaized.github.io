ARCHITECTURE BLUEPRINTS

See the system.
Then defend it.

Four reference architectures for security operations, drawn as animated diagrams you can step through. Generic patterns built on public standards, not a description of any real environment.

DETECTION & RESPONSE

From telemetry to decision.

A reference flow for a detection program. Each stage depends on the one before it, and the last stage feeds the first.

01
  1. SourcesTelemetry from endpoints, identity, cloud, network, and SaaS. A coverage gap here is invisible to every later stage.
  2. Collect and normalizeEvents are parsed into a common schema, given asset and identity context, and kept as searchable history for hunting.
  3. DetectRules, correlation, and anomaly logic turn events into alerts. Each rule needs an owner, a test, and a reason to exist.
  4. TriageAn analyst, supported by automation and past context, separates evidence from assumption and decides what the alert means.
  5. RespondContainment uses approved, reversible actions. A person authorizes anything consequential.
  6. LearnEvery case feeds back: tune noisy rules, add missing telemetry, and record what the next analyst will need.

INCIDENT RESPONSE

The response lifecycle.

The working loop behind every playbook on this site, following NIST SP 800-61 and the CSF 2.0 functions. Governance sits at the center of all six phases.

02
  1. PrepareRoles, contacts, access, tooling, and exercised playbooks exist before the incident. Preparation decides how the first hour goes.
  2. Detect and analyzeConfirm that it is an incident, set severity, scope the affected systems, and start a timeline.
  3. ContainLimit the damage while preserving evidence. Fast isolation first, durable containment next.
  4. EradicateRemove the attacker’s access: persistence, accounts, tooling, and the weakness that let them in.
  5. RecoverRestore from trusted sources in priority order, verify the result, and monitor for a return.
  6. ImproveReview without blame. Turn findings into detections, fixes, and updated playbooks, which is where preparation begins again.

AI FOR DEFENDERS

An agent with boundaries.

A pattern for giving an AI assistant a useful job in security operations without giving it the keys. The controls are enforced in code around the model, not inside its prompt.

03
  1. A defined taskOne alert, one job. The agent’s scope is that task and nothing broader.
  2. The agentThe model plans and reasons. It holds no standing credentials of its own.
  3. Read-only toolsEvidence is gathered through narrow, read-only queries. Tool output is treated as data, never as instructions.
  4. Policy gateCode, not the model, decides what is allowed. Reads pass. Anything that changes a system is held.
  5. Human approvalA person reviews the evidence and authorizes the action. Actions are designed to be reversible.
  6. The recordThe output shows its sources, confidence, and gaps, and every step is logged for later review.

IDENTITY & ACCESS

Access without implicit trust.

The zero trust request path described in NIST SP 800-207: every request is verified, decided, brokered, and observed. Being on the network earns nothing.

04
  1. The requestA person on a device asks for one resource. Network location earns no trust.
  2. Verify identity and deviceStrong sign-in proves who is asking. Posture checks prove the device is managed and healthy.
  3. DecidePolicy evaluates each request against current signals and grants the least access needed.
  4. BrokerA proxy creates a session to that one application. Nothing else on the network becomes reachable.
  5. AccessThe application and its data receive a verified, scoped session and still enforce their own authorization.
  6. ObserveEvery decision and session is logged, and a change in risk can end a session while it is in progress.

SHORT FILMS

Prefer to watch?

Each diagram as a short silent film with a written transcript. Nothing plays until you press play.

Patterns, not prescriptions.

These diagrams simplify on purpose. Real environments add constraints, exceptions, and history that no reference pattern captures. Use them to start a design conversation or to explain a control to someone new.
